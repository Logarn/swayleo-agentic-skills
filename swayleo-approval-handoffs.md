# Approval Handoffs

## Purpose and provenance

Recovered from brand-agent holds, review requests and task-state reconciliation.

This workflow applies across brands by substituting the current brand's sources, account, scope and approval rules. It is a reusable instruction set, not evidence that a live system is configured.

## Inputs

Current strategy/copy/design artifacts, approval messages, reviewer roles, task statuses, delivery dates and scope decisions.

If an input is unavailable, identify its effect and continue work that does not depend on it. Do not fill factual gaps with another brand's assumptions.

## Workflow

1. Map the actual approval chain for this brand. Internal review, client approval, copy delivery, design approval and build release are different states.
2. Read the latest explicit decision for each artifact/version. A review request, uploaded file, passing QA result or Copy Done status does not establish approval of downstream work.
3. Resolve later holds against older Start ASAP instructions. Preserve the old deadline as history; do not renew it automatically or let it override a hold.
4. Separate active revisions from unapproved new work. A hold on one batch does not stop every unrelated batch unless the instruction says so.
5. Update existing task records when authorized. Keep owners and original dates unless a real reassignment or revised commitment exists. Do not create duplicate review tasks or send duplicate requests.
6. For a handoff, state the exact deliverable/version, decision needed, reviewer, dependencies and next allowed stage. Make unresolved terms visible.
7. Draft communications unless sending is explicitly requested. If current tools cannot update one tracker, provide the precise pending correction.

## Deliverable

Artifact/version | Delivered | Internal review | Client approval | Release state | Next owner/action | Evidence. Include draft handoff text only when useful.

Use the output worksheet inside the downloadable library ZIP to structure a working draft. Adapt it to the requested deliverable; do not create extra files unless useful.

## Example

“Copy delivered” can coexist with “Design on hold.” Record both rather than changing the whole task to complete.

## Verification and completion

Approval tied to version; holds honored; revisions separated; existing records reused; owners/dates preserved; communication state accurate.

Report what was completed, the source or saved record that proves it, and any unresolved blocker. Distinguish a draft, a saved change and a live action. Publishing, posting, scheduling or changing live systems requires the corresponding user request and available tools.
